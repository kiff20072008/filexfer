# filexfer — передача файла между процессами (клиент + сервер)

Консольная программа для Linux на C++17: клиент и сервер в одном исполняемом файле.
Используются только стандартная библиотека C++ и системные вызовы POSIX/Linux, сторонних библиотек нет.

## Сборка

Нужны Linux, `g++` ≥ 7 или `clang++` ≥ 6, `make` или `cmake` ≥ 3.13.

```bash
make                 # -> ./filexfer
make test            # собрать и прогнать юнит- и интеграционные тесты
make asan            # сборка с AddressSanitizer + UBSan (программа и юнит-тесты)
```

или через CMake:

```bash
cmake -S . -B build && cmake --build build && ctest --test-dir build --output-on-failure
```

Без системы сборки: `g++ -std=c++17 -O2 -Isrc -o filexfer src/*.cpp`.

## Проверка за 2 минуты

Терминал 1 — сервер:

```bash
make && ./filexfer -s
```

Терминал 2 — клиент:

```bash
head -c 1G /dev/urandom > /tmp/big.bin

./filexfer -c /tmp/big.bin                      # обычная передача; в конце — имя файла на сервере
cmp /tmp/big.bin ./20261018_143005.hex          # подставьте имя из последней строки клиента

./filexfer -c /tmp/big.bin                      # нажмите Ctrl+C посреди передачи…
./filexfer -c /tmp/big.bin                      # …и запустите снова: «продолжаем с этого места»

head -c 5M /dev/urandom > /tmp/small.bin        # канал с потерей и искажением байтов в обе стороны
FILEXFER_FAULTS="drop=0.00003,flip=0.00003,dir=both" ./filexfer -c /tmp/small.bin

./filexfer -c /tmp/big.bin 127.0.0.1 6000       # сервера нет — клиент сразу сообщает об этом
top -p "$(pgrep -f 'filexfer -s')"              # сервер в ожидании: 0% CPU
```

Всё это автоматически проверяет `make test`.

## Структура

```
src/
  main.cpp              разбор аргументов, выбор режима, сборка транспорта
  transport.hpp         ITransport / IAcceptor / IConnector — абстракция канала
  link_params.hpp       окно и таймауты, которые задаёт транспорт (TCP / COM-порт)
  unique_fd.hpp         RAII-владелец файлового дескриптора
  fd_transport.*        транспорт поверх любого fd (сокет, tty, pipe)
  tcp_transport.*       TCP: TcpAcceptor (сервер), TcpConnector (клиент)
  fault_transport.*     декоратор, теряющий и искажающий байты, — имитация плохого канала
  protocol.*            формат кадров, Connection: буферы, CRC, ресинхронизация
  server.*              сервер: epoll, сессии, запись файлов
  client.*              клиент: окно отправки, повторы, переподключение, докачка
  util.*, log.*         CRC32, FNV-1a, сериализация, вывод сообщений
tests/
  unit_tests.cpp        юнит-тесты протокола и fault-транспорта (свой мини-фреймворк)
  run_tests.sh          интеграционные тесты реальных процессов
```

## Запуск

```bash
./filexfer -s [порт]                     # сервер, порт по умолчанию 5555
./filexfer -c <файл> [хост] [порт]       # клиент, по умолчанию 127.0.0.1:5555
```

- Сервер работает, пока его не остановят (`Ctrl+C` / `SIGTERM`), и принимает файлы от любого числа клиентов одновременно.
- Полученный файл сохраняется **в каталоге исполняемого файла сервера** (не в текущем каталоге) под именем
  `ГГГГММДД_ЧЧММСС.hex`, например `20261018_143005.hex`. Если в одну секунду пришло несколько файлов, добавляется
  суффикс: `20261018_143005_1.hex`.
- Клиент работает только на время передачи. Код возврата: `0` — файл принят сервером и проверен,
  `1` — ошибка, `2` — неверные аргументы, `130`/`143` — прерван через `Ctrl+C`/`SIGTERM`.

Пример (вывод сокращён):

```
$ ./filexfer -s
[14:30:01] [сервер] Запущен (TCP порт 5555). Каталог для файлов: /home/user/filexfer. Ожидание передачи…
[14:30:05] [сервер] Начало приема от 127.0.0.1:51234: «photo.jpg», 2481152 байт -> 20261018_143005.hex
[14:30:05] [сервер] Прием завершен: 20261018_143005.hex (2481152 байт, 0.1 с, 23.66 МБ/с)

$ ./filexfer -c photo.jpg
[14:30:05] [клиент] Начало передачи: «photo.jpg», 2481152 байт -> 127.0.0.1:5555
[14:30:05] [клиент] Передача завершена: «photo.jpg», 2481152 байт (0.1 с, повторов: 0). Сервер сохранил файл как 20261018_143005.hex
```

## Соответствие требованиям

| Требование | Реализация |
|---|---|
| Единый исполняемый файл, C++ под Linux, без сторонних библиотек | один бинарник `filexfer`, только libstdc++ и POSIX; тесты тоже без фреймворков |
| Сервер всегда ожидает приёма | цикл `epoll_wait`, завершается только по `SIGINT`/`SIGTERM` (через `signalfd`) |
| Клиент запускается только на время отправки | процесс завершается после подтверждения от сервера |
| Файл сохраняется в папке с программой как `date_time.hex` | каталог берётся из `/proc/self/exe`; запись в `*.hex.part`, затем атомарный `rename` |
| Сообщения о начале и завершении передачи | на обеих сторонах, с размером, скоростью и итоговым именем файла |
| `-s` — сервер, `-c <путь>` — клиент | да; принимается и `-с` с кириллической «с», как в тексте задания |
| **Плюс:** несколько клиентов одновременно | один поток, неблокирующие сокеты + `epoll`, у каждой передачи своя сессия |
| **Плюс:** не блокировать программу и не нагружать CPU | `epoll_wait` спит до события или ближайшего таймера; в простое 0 тиков CPU (проверяется тестом) |
| **Плюс:** контроль ошибок, неустойчивое соединение | CRC32 заголовка и данных каждого кадра, CRC32 всего файла, подтверждения, повторы, переподключение и докачка, в том числе после перезапуска процесса клиента |
| **Плюс:** работа с другим интерфейсом (COM-порт) | протокол работает поверх абстрактного потока байт `ITransport`; TCP — одна из реализаций; поведение на ненадёжном канале проверяется через `FaultyTransport` |

## Архитектура

```
 main ─┬─ Server (epoll, сессии, запись файлов)      Sender (клиент: окно, повторы, докачка)
       │            │                                         │
       │        Connection — кадры: заголовок + CRC32, буферы, поиск границы кадра после мусора
       │            │                                         │
       └── IAcceptor / IConnector / ITransport — неблокирующий поток байт с fd для poll/epoll
                    │
               TcpAcceptor / TcpConnector / FdTransport      (COM-порт: FdTransport поверх /dev/ttyS*)
                    │
               FaultyTransport / FaultyConnector — декоратор: потеря и искажение байтов (для тестов)
```

Логика клиента и сервера ничего не знает о TCP. Чтобы передавать через COM-порт, достаточно открыть
`/dev/ttyUSB0` с `O_NONBLOCK`, настроить `termios` (raw-режим, скорость) и отдать дескриптор в `FdTransport`;
`IConnector`/`IAcceptor` для порта возвращают единственное «соединение». Протокол для этого уже готов:
у каждого кадра есть magic и CRC заголовка, поэтому после потери или искажения байтов приёмник находит
начало следующего кадра, а потерянные данные запрашиваются повторно.

Все дескрипторы (сокеты, файлы, epoll, signalfd) принадлежат `UniqueFd`, ручных `close()` в коде нет.

### Параметры канала

Размер блока, окно и таймауты зависят от скорости линии: по TCP окно в 512 КиБ уходит за миллисекунды,
а по COM-порту на 115200 бод — за 45 секунд. Поэтому их задаёт транспорт через `params()` (`link_params.hpp`),
а клиент и сервер только читают. Для TCP используются значения по умолчанию; для последовательного
порта есть `serial_link_params(baud)`: окно — около двух секунд передачи, таймауты — с запасом
относительно времени передачи окна.

### Имитация плохого канала

`FaultyTransport` оборачивает любой транспорт и с заданной вероятностью теряет байты или инвертирует
в них случайный бит — на отправке, на приёме или в обе стороны. Так протокол проверяется в условиях
COM-порта с помехами, без железа. Включается переменной окружения на стороне клиента:

```bash
FILEXFER_FAULTS="drop=0.0001,flip=0.0001,seed=42,dir=both" ./filexfer -c file.bin
```

`dir=tx` (по умолчанию) — искажаются данные к серверу, `rx` — ответы сервера, `both` — всё.
Клиент сообщит о включённых помехах, а в итоговой строке покажет число повторов. Файл на сервере
совпадает с исходным побайтно.

## Протокол

Все числа big-endian. Кадр:

```
+-------+------+---------+--------+-------------+------------+----------------+
| magic | type | version | len    | crc_payload | crc_header | payload (len)  |
| 2     | 1    | 1       | 4      | 4           | 4          |                |
+-------+------+---------+--------+-------------+------------+----------------+
```

`crc_header` — CRC32 первых 12 байт. Кадр с неверным заголовком сдвигается на байт (ресинхронизация),
кадр с неверными данными отбрасывается, и сервер отвечает `NACK`.

| Сообщение | Направление | Содержимое |
|---|---|---|
| `START` | C→S | id(8), size(8), flags(1), name |
| `START_ACK` | S→C | id(8), offset(8), status(1), saved_name — с какого байта продолжать |
| `DATA` | C→S | offset(8), данные (до 32 КиБ) |
| `ACK` | S→C | next_offset(8) — кумулятивное подтверждение |
| `NACK` | S→C | expected_offset(8) — «повтори с этого места» |
| `END` | C→S | size(8), crc32 всего файла(4) |
| `DONE` | S→C | status(1), saved_name |

Обычная передача: `START → START_ACK(0) → DATA… (окно 512 КиБ, ACK по мере записи) → END → DONE`.
Сервер переименовывает `.part` в `.hex` только после совпадения размера и CRC32 всего файла.

`id` передачи — хеш имени, размера, времени изменения и CRC32 файла. Поэтому перезапущенный клиент
продолжает передачу с места обрыва. Если тот же файл одновременно отправляет другой клиент или файл
уже был принят, сервер заводит новую передачу с новым `id`.

## Поведение при сбоях

| Ситуация | Что происходит |
|---|---|
| Сервер не запущен | клиент сразу сообщает, что сервер недоступен, и завершается с кодом 1 |
| Обрыв соединения посреди передачи | клиент переподключается (до 10 попыток подряд без прогресса, пауза 2 с), сервер отвечает, с какого байта продолжать |
| `Ctrl+C` / `SIGTERM` клиента | клиент сообщает, сколько байт подтверждено, и завершается с кодом 130/143; повторный запуск в течение 60 с продолжает с этого места |
| Процесс клиента убит (`kill -9`) | сервер хранит недокачанный файл 60 с; повторный запуск клиента с тем же файлом продолжает с места обрыва; иначе `.part` удаляется |
| Искажение/потеря байтов (COM-порт) | кадр отбрасывается по CRC, `NACK`, клиент повторяет с подтверждённой позиции и уменьшает размер блока |
| Потерян `ACK` / `NACK` / `DONE` | клиент повторяет данные или `END` по таймауту, сервер повторяет отложенный `NACK`; 10 минут сервер помнит завершённые передачи и отвечает «уже принят» |
| Сервер завис или пропал | клиент через 15 с без ответа переподключается |
| Клиент «молчит» | сервер закрывает соединение через 30 с |
| Файл изменился во время отправки | расхождение CRC32 всего файла, сервер удаляет `.part`, клиент завершается с кодом 1 |
| Нет места на диске / ошибка записи | сервер прерывает приём, удаляет `.part`, сообщает клиенту причину |
| Кончились файловые дескрипторы | новое соединение отклоняется, сервер не уходит в холостой цикл |
| Сервер остановлен (`SIGTERM`) или упал | недокачанные `.part` удаляются при остановке или при следующем запуске |

Таймауты в таблице — для TCP; для других каналов их задаёт транспорт (см. «Параметры канала»).

## Тесты

```bash
make test
```

**Юнит-тесты** (`tests/unit_tests.cpp`, 25 тестов, без сторонних фреймворков): CRC32 и FNV-1a на эталонных
значениях, сериализация и защита от выхода за границы, кадрирование поверх транспорта в памяти
(частичная запись, приход по одному байту), ресинхронизация после мусора, отбрасывание кадров с битыми
данными или заголовком, отказ от кадров с длиной больше лимита и чужой версией. Fault-транспорт: разбор
параметров, прозрачность без помех, корректный учёт байтов при частичной записи, детерминированность,
помехи на приёме (полная потеря — это «нет данных», а не закрытие соединения). Параметры канала:
согласованность таймаутов для скоростей от 1200 бод до 4 Мбод. Главные тесты: через канал с потерей
и искажением байтов на отправке и на приёме проходят сотни кадров, и ни один испорченный кадр не доходит
до получателя.

**Интеграционные тесты** (`tests/run_tests.sh`): поднимают сервер на случайном порту и проверяют
обычную передачу, пустой файл, большой файл (64 МиБ), имена с пробелами и кириллицей, формат имени,
сообщения о начале и завершении, коды возврата, 8 параллельных клиентов, одновременную отправку одного
файла, передачу через канал с помехами в обе стороны, быстрый отказ без сервера, `Ctrl+C` клиента
с последующей докачкой, докачку после `kill -9` клиента (512 МиБ), отсутствие нагрузки на CPU
в простое и корректную остановку сервера.

**CI** (GitHub Actions): сборка gcc и clang с `-Werror`, сборка с AddressSanitizer + UBSan, CMake + CTest;
на каждой — юнит- и интеграционные тесты.

## Принятые решения

- **`.hex`** понимается как требование к имени файла: содержимое сохраняется байт в байт, без перекодирования.
- **«Папка с программой»** — каталог исполняемого файла (`/proc/self/exe`), а не текущий каталог.
- **Хост и порт** — необязательные параметры после обязательных из задания, чтобы клиент и сервер можно
  было запускать на разных машинах.
- **Один поток + epoll** вместо потока на клиента: нет синхронизации, предсказуемое потребление ресурсов,
  ноль CPU в ожидании.
- **Подтверждения поверх TCP** избыточны для доставки, но нужны для докачки после обрыва и для каналов
  без гарантий доставки (COM-порт).
- **Сервер недоступен с самого начала — сразу ошибка.** Долгие повторы нужны, когда связь пропала
  посреди передачи, а не когда сервер просто не запущен.

## Ограничения

- Состояние недокачанных передач хранится в памяти сервера: после перезапуска сервера передача начинается заново.
- Запись на диск (`pwrite`, `fdatasync`) синхронная, в том же потоке; на очень медленном диске она задерживает
  остальных клиентов.
- Реализован только TCP-транспорт; COM-порт подключается новым классом (см. «Архитектура»), параметры
  для него уже есть (`serial_link_params`).
- Только IPv4. Нет аутентификации и шифрования: передача предполагается в доверенной сети.
